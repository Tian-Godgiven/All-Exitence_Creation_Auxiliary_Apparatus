# 领域模型与存储盘点

本文件记录重构开始时的真实模型和存储分布，不代表后续正式结构。

## 项目

`ProjectInfo`：`name`、`pathName`、`time`、可选 `info`、`lastTarget`。

项目根目录位于应用本地数据的 `data/projects/<pathName>/`，核心文件为：

| 文件 | 内容 |
| --- | --- |
| `projectInfo.json` | 项目资料与上次主视图目标 |
| `all-articles.json` | 根章节与根文章 |
| `all-exitence.json` | 全部分类、分组、事物与属性 |
| `data/` | 项目级辅助功能数据 |

## 文章树

| 对象 | 字段与关系 |
| --- | --- |
| `Chapter` | `name`、`articles`、`chapters`、`from`、`__key`、`expending` |
| `Article` | `title`、`inner`、`from`、`__key`、`createTime`、`updateTime`、`lastScrollTop` |

章节与文章通过 `from: string[]` 保存其祖先章节键路径；根层路径为空。嵌套结构同时以 `Chapter.chapters` 和 `Chapter.articles` 持有。

## 分类树与事物

| 对象 | 字段与关系 |
| --- | --- |
| `Type`（分类） | `name`、`typeStatus`、`setting`、`groups`、`exitence`、`__key`、`expending` |
| `Group`（分组） | `name`、`rules`、`setting`、`__key`、`typeKey`、`expending` |
| `Exitence`（事物） | `name`、`status`、`typeKey`、`setting`、`__key`、`lastScrollTop` |
| `Status`（分类属性） | `name`、`value`、`valueType`、`setting`、`__key` |
| `ExitenceStatus`（事物属性） | `__key`、`value`；可覆盖 `name`、`valueType`、`setting` |

`Exitence.typeKey` 与 `Group.typeKey` 指向分类。事物属性以同一个 `__key` 对应分类属性；读取完整属性时合并分类属性与事物覆盖值。分组不是事物容器，而是通过规则动态筛选所属分类的事物。

| 功能 | 范围 | 当前文件 |
| --- | --- | --- |
| 输入建议 | 全局 + 项目 | `data/appData/globalInputSuggestionList.json`；项目 `data/inputSuggestionList.json` |

未启用的任务清单和时间线有各自文件读写实现，但不属于当前运行模型。

## 已确认的重构决策

### 文章树

保留嵌套数组和 `from` 路径两种表达：嵌套数组服务于结构与渲染，`from` 服务于父级定位、聚焦与跳转。

两者必须由统一的创建、移动与删除操作维护；组件不得自行修改数组或路径。移动章节时，需要递归更新被移动章节、其子章节和其中文章的 `from` 路径。后续应提供校验或重建路径的工具，防止持久化数据出现不一致。

### 删除与回收站

回收站与永久删除并存。普通删除先进入应用级统一回收站；用户在回收站中执行永久删除后才真正清除。

回收站的核心对象是文章和事物。删除章节或分类等容器时，也需保留该容器快照及其包含的文章或事物，确保可以按原有层级恢复。分组是动态筛选规则，不是事物容器；删除分组不删除其中的事物。

每次删除容器只创建一条回收记录，保存容器及其全部后代的完整快照，恢复时整体恢复，避免一条删除操作产生大量相互依赖的回收记录。回收记录还应保存原项目、删除时间、原父级与原排序位置；若原父级已不存在，则恢复到相应树的根层。

删除项目同样进入应用级回收站，而不是直接永久删除。删除项目时保留完整项目目录；删除项目内对象时，保存带来源信息的独立回收记录与快照。若恢复项目内对象时原项目已经在回收站，需先恢复原项目或由用户选择新的恢复目标。

### 唯一标识

保留现有的 `__key` 字段，不进行全量重命名。它已经由 `nanoid` 生成，并作为项目、章节、文章、分类、分组、事物和属性的不可变唯一标识。名称可编辑，`__key` 不可编辑。

### 属性值

不以消灭 `any` 为目标。先盘点实际 `valueType`、现有持久化内容与界面需求，再决定哪些值保留自由 JSON，哪些建立明确数据结构。

## 结构问题，留待设计阶段决定

1. 保存职责分散：项目核心文件、项目辅助功能文件、全局辅助功能文件由不同模块直接写入。
2. `setting`、`value`、文章 `inner` 广泛使用宽泛值，不能仅靠替换为类型别名解决，必须先定义各值类型的真实边界。
3. `from` 路径和嵌套数组同时表达文章树关系，移动、删除和恢复时需要保持一致；保留两者的维护规则已确认。
4. 当前文件没有格式版本字段；由于尚未正式发布，可在新存储格式设计中直接加入 `formatVersion`。
