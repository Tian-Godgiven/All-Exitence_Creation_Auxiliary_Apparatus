# 本地存储格式设计

本设计用于重构后的新项目数据，不兼容当前非正式阶段的 JSON 数据。

## 目录布局

```text
AppLocalData/
  data/
    app.json
    features/
      input-suggestion.json
      custom-time.json
    projects/
      <project-__key>/
        project.json
        articles.json
        exitence.json
        features/
          input-suggestion.json
          quick-draft.json
          tag-library.json
    trash/
      index.json
      records/
        <trash-record-__key>.json
      projects/
        <trash-record-__key>/
          project/
            project.json
            articles.json
            exitence.json
            features/
              ...
```

项目目录以不可变的项目 `__key` 命名。项目名称只保存在项目资料中，改名不再涉及文件夹改名。

## 文件职责

| 文件 | 职责 |
| --- | --- |
| `app.json` | 应用设置、上次打开项目和应用级数据版本 |
| `features/*.json` | 各全局辅助功能独立维护的数据 |
| `project.json` | 项目 `__key`、名称、简介、创建/更新时间、上次查看目标和项目数据版本 |
| `articles.json` | 文章与章节树 |
| `exitence.json` | 分类、分组、事物和属性 |
| `features/*.json` | 对应项目级辅助功能的数据 |
| `trash/index.json` | 全局回收站的可浏览记录摘要 |
| `trash/records/*.json` | 已删除项目内对象的完整回收记录与快照 |
| `trash/projects/<record>/project/` | 已删除项目的完整目录快照 |

自定义时间等全局能力不属于项目 `features/`，其数据分别保存在 `data/features/` 下的独立文件中。

## 版本规则

每个核心 JSON 文件的顶层带 `formatVersion`，而非为每个领域对象重复添加版本号。例如：

```json
{
  "formatVersion": 1,
  "articles": [],
  "chapters": []
}
```

未来版本先根据 `formatVersion` 判断是否需要迁移。当前重构阶段不提供旧格式自动迁移。

## 回收记录

删除项目内对象时，在 `trash/records/` 创建一条记录，并在 `trash/index.json` 创建其摘要。记录结构如下：

```json
{
  "formatVersion": 1,
  "__key": "回收记录 id",
  "kind": "article",
  "deletedAt": 0,
  "projectKey": "原项目 id",
  "parent": {
    "kind": "chapter",
    "__key": "原父级 id"
  },
  "index": 2,
  "snapshot": {}
}
```

- `kind` 可为文章、章节、事物、分类或其他将来允许回收的对象类型。
- 删除章节或分类时，`snapshot` 是包含其全部后代的完整容器快照。
- `parent` 和 `index` 用于恢复原位置；原父级不存在时恢复到对应根层。
- 删除分组不删除事物；分组可作为独立记录，但不包含动态筛选出的事物。

删除项目时，完整项目目录移动到 `trash/projects/<record>/project/`。该回收记录保存项目的摘要与删除时间，不把项目内容复制进 JSON。

恢复项目内对象时，优先恢复到原项目。若原项目仍在回收站，需先恢复该项目或由用户选择另一个项目作为恢复目标。

## 清理规则

第一版不自动清理回收站。只有用户主动执行永久删除时，才删除对应的记录与快照。

## 开发期数据切换

当前项目尚未正式发布，不为现有 JSON 编写自动迁移器。新存储格式落地后，旧测试项目不保证可打开。

开发期将提供明确的“重置应用数据”工具：清除当前应用本地数据后，按新格式重新初始化应用目录。该工具必须在执行前二次确认，并明确提示其会删除活跃项目、回收站和应用设置；具体实现与入口在单独审批后进行。

正式版前再设计用户可见的备份、导出、导入、数据升级与迁移策略。

## 保存策略

项目采用全量保存：每次保存覆盖该项目的 `project.json`、`articles.json` 与 `exitence.json`，并保存本次发生变化的项目级辅助功能文件。当前不做对象级增量写入或数据库化存储。

同一项目的保存请求必须串行执行，后一次保存应等待前一次完成，避免并发写入相互覆盖。写入 JSON 时应先写入同目录临时文件，写入成功后再替换正式文件；发生错误时保留原正式文件并将失败结果返回给上层。

## 文件错误处理

| 情况 | 处理方式 |
| --- | --- |
| 缺少非核心辅助功能文件 | 视为空数据，并创建该功能的默认文件 |
| 缺少或无法解析 `project.json`、`articles.json`、`exitence.json` | 不自动覆盖；在项目列表中标记为无法读取，并提供查看错误、导出原始文件、删除或从备份恢复的入口 |
| 单个辅助功能文件损坏 | 不阻止项目打开；只禁用对应功能，显示错误状态，并提供“重置此功能数据”按钮 |
| 重置辅助功能数据 | 用户二次确认后，以该功能默认数据重建对应文件；不影响项目核心数据或其他辅助功能 |
| 保存失败 | 保留内存修改并提示用户重试；不得将失败状态标记为已保存 |

项目级辅助功能文件统一使用 `{ "formatVersion": 1, "data": ... }` 的外层结构。仓储层只负责该结构的读写；每项功能自身负责提供默认数据，并在用户确认重置后将默认数据保存回自己的文件。
