# 重构计划

## 目标

在不改变产品核心方向的前提下，整理现有实现，使项目能够稳定地继续完成既有功能，并为后续正式版建立可维护的基础。

本轮重构是内部实现调整，不是产品重做。

## 当前决策

1. 当前 JSON 项目数据不需要兼容。项目仍处于非正式阶段，允许按新的领域模型和存储结构调整或重建测试数据。
2. 暂不引入数据库。应用是本地离线创作工具；项目数据仍以本地文件存储。联网能力仅在确有需要时单独设计，例如检查更新。
3. 不因重构而改变已经认可的产品功能和范围。功能调整需要作为独立需求讨论。
4. 不预先引入 Pinia、编辑器框架或其他大型依赖。只有在明确解决具体问题并获批准后才考虑。

## 审批规则

1. 所有写入性改动均须在实施前获得批准，包括源代码、配置、依赖、数据结构、脚本、删除或移动文件。
2. 每次申请只包含一个可独立验证的改动单元；说明目标、涉及文件、行为影响、数据影响和验证方式。
3. 获得批准后才实施该单元，完成后报告实际改动和验证结果，再申请下一个单元。
4. 允许不经批准进行只读检查、代码阅读、构建诊断和方案讨论；这些操作不会修改工作区。
5. 文档记录本身按本次授权维护；若文档会改变产品需求或技术决策，也先讨论确认。

## 重构原则

- 先建立可运行、可验证的基线，再调整内部结构。
- 先处理数据流、持久化和领域模型，再处理 UI 组件拆分与交互优化。
- 每个改动保持小范围、可回归验证、可单独审阅。
- 新数据格式应有明确版本号与迁移入口，即使当前不需要兼容旧 JSON。
- 领域逻辑不依赖 Vue 组件或 Tauri 文件 API；界面只负责呈现与触发操作。
